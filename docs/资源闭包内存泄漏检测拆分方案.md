# 资源、闭包与内存泄漏检测拆分方案

> 2026-09-29 源码审查记录。本文描述当前检出的代码路径、问题与拟议方案；没有运行应用、基准或对三类缺陷测量准确率。文中的“可行”指现有代码结构允许渐进拆分，不代表新检测能力已经实现或验证。

资源泄漏检查第一阶段的目标、目录迁移、HomeFlow 对照范围与真实应用验收，见[资源泄漏检测第一阶段设计](./资源泄漏检测第一阶段设计.md)。

## 1. 先确定三类缺陷的判定对象

| 检查 | 要证明的事情 | 典型事实与释放/终止事件 | 不能直接推出的结论 |
| --- | --- | --- | --- |
| 资源泄漏 | 获得了有明确生命周期的句柄，在应释放的边界仍可能持有未释放状态 | `AVPlayer`、文件句柄、`PixelMap`、`Worker`；`release`、`close`、`terminate` | “某方法内没有 `release`”不等于泄漏；资源可能转交给调用方或在后续生命周期释放。 |
| 闭包泄漏 | 长寿命注册者继续持有回调，回调又保留了本应结束生命周期的对象 | `on`/`off`、`setInterval`/`clearInterval`；注册者、事件标识、回调身份、捕获对象 | 只发现未取消订阅，尚不能证明回调捕获了对象；宜先称“未取消注册/潜在闭包持有”。 |
| 内存泄漏 | 对象在预期生命周期后仍从长寿命根可达，导致不必要的保留 | 根、引用关系、对象/组件生命周期、逃逸或覆盖证据 | `new ArrayBuffer`、大对象分配本身不等于泄漏；`PixelMap.release` 缺失首先是资源生命周期问题。 |

三类检查可以共用 ArkIR、调用/回调关系、生命周期入口、IFDS 基础设施、值和别名工具、位置提取，但**判定条件和报告证据不能只靠规则的 `category` 字段切换**。一项缺陷可能同时造成资源占用和内存增长；报告应按直接违反的义务确定主类别，必要时附带影响标签，通过同一分配点/注册点关联，避免重复计数。

## 2. ArkLifeguard 当前实现

### 2.1 对外只有一个资源检查

`ProjectAnalyzer` 的 `runResourceAnalysis` 分支顺序运行跨过程 `TaintAnalysisRunner`、方法内 `ResourceLeakDetector`、`SourceSinkLocationScanner`，并统一写入 `resourceAnalysis`。`--checks resource` 尚不能分别选择上述三类检查。IFDS 结果与方法内候选已分开存放，见 [应用编排](../src/application/ProjectAnalyzer.ts) 和 [使用说明](../QUICKSTART.md)。

| 部件 | 当前责任 | 能力边界 |
| --- | --- | --- |
| [SourceSinkManager](../src/analysis/resource/SourceSinkManager.ts) | 单个默认规则表与方法名/签名匹配；规则具有 `resource`、`closure`、`memory` 分类 | `isSource`/`isSink` 各返回首个匹配项，而不是全部规则；类别不是独立检查开关。 |
| [TaintFact](../src/analysis/resource/TaintFact.ts)、[TaintAnalysisProblem](../src/analysis/resource/TaintAnalysisProblem.ts)、[TaintAnalysisSolver](../src/analysis/resource/TaintAnalysisSolver.ts) | IFDS 事实传播、Source 生成、Sink 识别、剩余活跃事实报告、生命周期入口、结果抑制 | 目前同一个 Problem 和结果集合承载所有类别；`getTaintLeaks()` 当前无填充路径，不能视为隐私泄漏检查。 |
| [ResourceLeakDetector](../src/analysis/resource/ResourceLeakDetector.ts) | 两遍扫描方法内的申请和释放，给出候选 | 只接受赋值到 `Local` 的、`returnTainted` 的 Source；不证明路径顺序、所有出口或跨方法所有权。 |
| [SourceSinkLocationScanner](../src/analysis/resource/SourceSinkLocationScanner.ts) | 枚举规则命中的 Source/Sink 调用位置 | 只做命中和定位，不产生泄漏判定。 |
| `LifecycleLeakSuppressor`、`FileLeakSuppressor` | 对定时器和文件候选做结构性抑制 | 目前放在 `TaintAnalysisSolver.ts` 中，属于结果策略，不属于通用 IFDS 求解器。 |

当前规则实例包括：

- `resource`：媒体/图像/文件/网络/数据库等句柄，也包含 `sensor.on`、`geoLocationManager.on` 和 CommonEvent 订阅。
- `closure`：定时器、事件监听、窗口/显示回调、分布式对象监听等。
- `memory`：`image.createPixelMap.memory`、`new ArrayBuffer`、`new Worker`、`new ThreadWorker`。其中 `image.createPixelMap` 另有 `resource` 规则。

`TaintCategory` 虽声明了 `sensitive_data`，默认 Source 表没有对应规则。当前 `taintLeaks` 字段主要是接口兼容，不能据此声称存在独立的数据泄漏分析，见 [README](../README.md)。

按**实际检测路径**而非规则名概括，当前能力是：

| 目标 | 当前状态 |
| --- | --- |
| 资源未释放 | 有跨过程 IFDS 候选和方法内候选；仍需核实 Source/Sink 配对、路径出口和所有权。 |
| 闭包未释放 | 定时器返回 ID 的部分情况进入 IFDS；多数不返回句柄的监听注册仅能在规则扫描中看到调用位置，尚无独立注册事实及捕获对象证据。 |
| 托管内存保留 | 没有独立保留链分析；`memory` 标签下的规则主要是分配点或显式终止义务。 |

### 2.2 问题与直接后果

1. **规则类别与实际检测能力不一致。** 许多监听/订阅规则的 `returnTainted=false` 且 `taintedParamIndices` 为空。当前 IFDS Source 生成只处理 `returnTainted` 的赋值调用，以及特殊的 `setInterval` 无接收值调用；普通 `on(...)` 不会因被标为 `closure` 就自动产生注册事实。方法内检测也只接受返回值赋给 `Local` 的 Source。`taintedParamIndices` 尚未接入这两条 Source 生成路径。位置扫描仍会列出这些调用，但这只是命中清单。[规则示例](../src/analysis/resource/SourceSinkManager.ts)、[IFDS Source 生成](../src/analysis/resource/TaintAnalysisProblem.ts)、[方法内 Source 识别](../src/analysis/resource/ResourceLeakDetector.ts)。
2. **首匹配丢失多重语义。** `isSource` 返回首个精确或通配匹配；`image.createPixelMap` 同时出现在 `resource` 和 `memory` 规则里，不能把规则表中两条记录理解成会产生两个独立诊断。需要先定义同一调用的主缺陷类别及共享证据，再决定是否支持多规则命中。[匹配逻辑](../src/analysis/resource/SourceSinkManager.ts)。
3. **释放匹配缺乏类别和配对约束。** IFDS 的 `checkSink` 只检查污染的接收者或参数，未验证当前 Source 与 Sink 的规则配对；匹配后按 Source 语句从全局 `activeTaints` 删除。不同释放 API 或不同分支相遇时，可能少报；这属于源码推断，尚需针对性夹具验证。方法内检测虽检查配对，但使用两遍全方法扫描，可能把其他分支或申请之前的释放视为有效。[IFDS Sink 处理](../src/analysis/resource/TaintAnalysisProblem.ts)、[方法内扫描](../src/analysis/resource/ResourceLeakDetector.ts)。
4. **“内存泄漏”规则混合不同机制。** `PixelMap` 与 `Worker` 的释放/终止是可检查的显式义务，适合先归入资源检查；`ArrayBuffer` 没有配对释放义务，仅有分配点不足以判断托管内存保留。现有代码没有建立长寿命根到对象的保留链，也没有在生命周期终点判断不可预期可达性。[规则片段](../src/analysis/resource/SourceSinkManager.ts)。
5. **结果缺少独立状态与证据。** 当前 `resourceAnalysis` 只有整体 `success`，IFDS 的所有活跃规则都汇入 `resourceLeaks`；方法内候选虽独立列出，却不按主类别隔离。拆分后若沿用这些字段，会混淆“未运行”“运行无发现”“部分失败”。[结果组装](../src/application/ProjectAnalyzer.ts)。

上述均是**当前源码可见的结构或由代码推得的风险**；本文不据此给出真实应用上的 TP/FP/FN 或性能变化。

## 4. 拆分可行性与目标边界

**结论：适合渐进拆分三种检查语义，不适合先把现有三类规则各搬进一个目录便宣布完成。** 现有 IFDS 求解器、生命周期 `DummyMain` 和报告编排已有可复用边界；本次方案无需重写通用 IFDS。困难在于“注册事实”“显式资源句柄”“托管内存保留”所需事实和终点条件不同，而且当前规则的类别并不等于实际检出覆盖。

建议的模块边界如下，名称为拟议结构：

```text
src/analysis/
  shared/               ArkIR 调用定位、规则解析、位置与别名辅助（仅放真正共用部分）
  resource/             显式申请/释放义务；IFDS Fact/Problem、方法内候选、规则、结果策略
  closure/              注册/取消义务、回调身份与捕获关系、长寿命持有证据
  memory/               生命周期后可达性/保留链；先做研究和夹具，不复用资源结论冒名输出
```

共享层只负责“哪个调用、哪个值、哪个生命周期边界”；领域分析负责“什么事实产生、如何传播、何时解除义务、何处报告”。异步回调的可执行性与时序应由 ICFG/生命周期建模提供，领域分析再处理回调捕获与资源事实传播；不能把注册调用的回调直接当作同步调用。

规则模型建议先从现有 `SourceDefinition`/`SinkDefinition` 扩充可验证的语义字段，再迁移存储位置：匹配签名、稳定规则 ID、主类别、产生事实的位置（返回值/参数/接收者/静态注册）、对应解除事件、事件标识和回调参数位置、生命周期边界。一个 API 可被多个规则描述，但匹配器需返回全部候选，由各领域分析按自己的条件筛选；同一实际义务使用同一分配/注册身份去重。对没有明确解除事件的规则，必须给出保留链证据或标为未支持，不以 `expectedSink=unknown` 充当泄漏结论。

### 4.1 三类检查的最小输出契约

| 检查 | 最低证据 | 结果名称建议 |
| --- | --- | --- |
| 资源 | 规则 ID、分配点、句柄/别名、应释放的生命周期边界、实际释放点或未释放出口、逃逸/转交状态 | `resourceLeaks` |
| 闭包 | 注册点、注册者范围、事件/定时器标识、回调身份、取消点；若声称“闭包泄漏”，还需捕获对象及生命周期关系 | `registrationLeaks`；证据足够时再细分 `closureRetentionLeaks` |
| 内存 | 长寿命根、到被保留对象的引用链、预期结束的生命周期、保留链在该边界仍可能存在的依据 | `memoryRetentionCandidates`，确立判定与基准后再使用 `memoryLeaks` |

默认报告可保留总览，但必须分别标识 `enabled`、`success`、数量和诊断。`taintLeaks` 不应被解释为这三类之一。`methodLocal` 保留为候选/辅助结果，不并入跨过程确认数量。报告 schema 改动应明确版本与旧字段迁移方式。

## 5. 实施顺序与验收条件

### 阶段 A：固定现状并梳理规则

1. 导出每条现有规则的 ID、API、当前类别、句柄来源、配对 Sink、生命周期边界、是否真的可生成事实；记录同一 API 的重复规则以及无释放义务的规则。
2. 明确初始归属：`PixelMap`、`Worker` 等按显式释放义务放进资源；事件/定时器注册放进注册检查；`ArrayBuffer` 先退出泄漏结论，等待保留链模型。`sensor.on`、定位/CommonEvent 等当前标为 `resource` 的注册 API 逐条复核，不能只按旧标签迁移。
3. 固定现有诊断快照及配置，建立“旧结果 → 新类别/不再报告/待验证”的逐条映射；历史结果只作基线，不作为新方案准确率证明。

**验收：** 每条默认规则有明确归属和支持状态；同一调用不会因多条规则无意重复计数；未支持规则可见且不会产生冒名诊断。

### 阶段 B：先稳住资源检查，再分出注册检查

1. 资源侧保留当前 IFDS 接口，先让 Source/Sink 按同一规则 ID 或明确配对关系匹配；以分配点和路径/出口状态生成候选，处理赋值别名、跨方法返回、字段转交、分支部分释放。
2. 将方法内扫描、定时器/文件抑制及位置扫描从求解器职责中分离；方法内候选保持较低证据等级，结构性抑制须标记理由，不把“发现任意 close/off”当作同一实例已释放。
3. 注册侧建立注册事实：`owner + event/timer ID + callback identity + registration site`；将 `on`、订阅和定时器的创建/取消接入独立规则。对捕获对象、注册者寿命证据不足的结果只报“未取消注册”。复用生命周期入口，但独立判断 `off` 的标识与回调是否匹配。

**验收：** AVPlayer、文件、PixelMap 的已释放/未释放与分支样例；定时器和 `emitter` 的正确取消、错误回调、错误事件、跨生命周期取消、未取消样例均有 TP/FP/FN 对照。资源和注册结果可单独启用；两类同时开启与单独开启时，同一类别诊断一致。

### 阶段 C：研究内存保留检查

1. 先定义可观察的长寿命根、目标对象与生命周期终点，例如全局/静态容器、长寿命系统注册者、已销毁组件及其字段。明确哪些边需要指针分析或保守近似。
2. 从小夹具验证 `root → listener → closure → component` 或 `root → container → object` 保留链；同时加入对象正常脱离、显式取消、无法确定逃逸等反例。
3. 只有存在保留链证据和非空诊断真值集后，才把该检查标成独立 `memory` 能力；否则维持研究状态，报告不得把大对象分配或资源未释放自动重命名为内存泄漏。

**验收：** 每条内存候选附生命周期边界和保留链；与资源/注册检查的重叠关系可解释；有针对性 TP/FP/FN 与未支持情形记录。

### 验证原则

- 先做直接相关的静态检查、规则单测、三类最小正反夹具和应用层报告契约测试；不把移动文件后的测试通过当成新语义已验证。
- 对比性能或精度时固定项目、SDK、入口模型、边界和超时；核对诊断集合与 `processedEdges`、`propagationAttempts`、`finalPathEdgeCount`，再比较耗时。历史记录不能替代拆分后版本的实测。
- 不为文档阶段运行完整测试套件、全量构建或真实应用基准。实施阶段若单项测试预计超过 2 分钟，按仓库 `AGENTS.md` 先征询用户。

## 6. 本文尚未解决的设计选择

1. “闭包泄漏”产品名是否仅用于有捕获/寿命证据的告警，其他情况称“注册未取消”：建议如此，以免过度声称。
2. `PixelMap`、`Worker` 等同时有内存影响的缺陷是否多报：建议一个主诊断，附影响标签；只有两条独立证据链成立才报两个问题。
3. 跨生命周期报告边界如何确定：应针对 Ability、Component、Page 分别建夹具；不能把任意方法返回作为所有资源的泄漏终点。
4. 旧 `resourceAnalysis` JSON 的兼容期限与新 `--checks` 名称：在有消费者清单和报告契约测试后定稿。
