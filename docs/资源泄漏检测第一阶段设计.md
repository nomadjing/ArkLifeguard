# 第一阶段：独立资源泄漏分析设计与 HomeFlow 对照验收

> 状态：2026-09-29 设计稿；第 3.1 节的目录与引擎接线已实施，规则与 IFDS 语义尚未实现。本文规定**预期目标、实现步骤和通过条件**，不引用旧日志作为本阶段的实验结论；真实应用对照是后续实施的验收门槛。

## 1. 范围与“同级能力”的含义

本阶段在 `src/analysis/resourceleak/` 建立**新的**资源泄漏分析实现，旧分析完整保留并可独立运行。在同一真实应用输入上，目标是覆盖 HomeFlow `ResourceLeak` 检查中 `resourceType=resource` 的规则和主要资源生命周期语义，而不以复制 HomeFlow 文件、告警总数相等或目录改名作为完成标志。

现有混合分析保留在原来的 [`src/analysis/resource/`](../src/analysis/resource/index.ts)，新模块独立位于 [`src/analysis/resourceleak/`](../src/analysis/resourceleak/index.ts)。原目录及公开导入路径不变；新模块只定义新的资源泄漏事实、规则、分析问题和结果。

HomeFlow 当前 [规则表](../../homeflow/config/checkerConfig.json)的 `ResourceLeak` 检查共 23 条默认规则：10 条 `resource`、13 条 `listener`（本次源码快照）。本阶段的 HomeFlow 对照范围是这 **10 条 `resource` 规则**；13 条 `listener` 留待闭包/注册检查阶段。HomeFlow 的资源标签中还有三条注册或定时器义务，先作为兼容范围覆盖，后续再决定归属：

| 本阶段分组 | HomeFlow 规则 ID | 本阶段要求 |
| --- | --- | --- |
| 明确句柄释放，7 条 | `RpcMessageSequenceNotRelease`、`ComponentContentNotRelease`、`AnimatorResultNotRelease`、`ImageSourceNotRelease`、`PixelMapNotRelease`、`AVPlayerNotRelease`、`BuilderNodeNotRelease` | 新资源分析的核心能力；多创建/多释放 API 逐条落实。 |
| 跨类别兼容，3 条 | `CommonEventSubscriberNotRelease`、`CommonEventSubscriberNotSetNull`、`SetIntervalNotRelease` | 为与 HomeFlow 的 `resource` 结果对照而纳入，规则标记 `compatibility`；涉及订阅或定时器的语义后续移交闭包/注册检查，不在本阶段宣称已检测一般闭包泄漏。 |

旧实现中的文件、网络、数据库、媒体等其他资源规则不删除。它们不在 HomeFlow 这 10 条规则的直接对照分母里，后续按新规则模型迁入并单独验证；不能因为新实现暂时没有这些规则就把旧实现切换为默认。当前 [ProjectAnalyzer](../src/application/ProjectAnalyzer.ts) 同时运行旧 IFDS、方法内检测和位置扫描；新旧诊断必须分开输出，不能混合计数。

这里的“达到 HomeFlow 同级”需同时满足：**规则覆盖、传播/释放语义、证据型报告、真实应用对照**四道门槛。HomeFlow 是可复现的比较基线，**不是正确性真值**；相同数量可能来自不同位置的误报与漏报，差异必须回到源码与平台 API 语义裁决。

## 2. 预期分析能力

| 能力 | 具体目标 | 可观察结果 |
| --- | --- | --- |
| 规则解析 | 规则以稳定 ID 绑定精确 API 身份与创建/释放配对；支持返回值、参数、接收者、静态注册等句柄来源。初始化时校验规则唯一性、配对与 SDK 可解析性。 | 每条规则给出 `loaded / unresolved / disabled` 和原因；同名但不同类/模块 API 不互相释放。参照 [HomeFlow LeakConfig](../../homeflow/src/resourceLeak/LeakConfig.ts)。 |
| 资源事实 | 以规则 ID、创建语句、资源句柄/别名、所属生命周期、状态为核心；状态至少区分 `allocated`、`released`、`escaped`、`unknown`。 | 同一分配点的不同资源、不同路径状态不被全局 Map 合并；复制变量后仍能找到原始分配。参照 [HomeFlow LeakFact](../../homeflow/src/resourceLeak/LeakFact.ts)。 |
| 过程内传播 | 赋值、字段读写、别名、覆盖、条件分支和多个出口；仅释放同一规则允许的同一资源。 | `if` 仅一支释放时保留“部分路径未释放”证据；覆盖丢失最后句柄时可独立报告；错误释放不抹掉原事实。 |
| 跨过程与异步边界 | 参数/返回值/接收者、字段转交、回调/Promise 中的资源创建与释放、生命周期方法之间的传播；明确所有权移交与未知调用的保守策略。 | `onCreate` 创建、`onDestroy` 释放不报；返回句柄给调用者不在被调方法出口直接误报；无法确认回调执行时保留不确定性。参照 [HomeFlow 四类流函数](../../homeflow/src/resourceLeak/LeakFlowFunctionProvider.ts)。 |
| 出口与报告 | 从 IFDS 可达出口事实生成候选，再做可解释的去重和抑制；区分未释放、部分释放、覆盖、错误释放与不确定所有权。 | 诊断至少包含规则 ID、分配点、泄漏边界、类型、证据路径/关键节点、原因与置信度；`unknown` 不伪装为确定泄漏。参照 [HomeFlow PostProcess](../../homeflow/src/resourceLeak/PostProcess.ts)。 |
| 单独运行 | 新资源分析有独立 Runner 与报告分区，不隐式合并旧方法内候选或闭包/内存类别。 | 同一工程可选择 `legacy`、`new` 做对照；单独运行新实现不改变旧实现输出。 |

**语义界限：** 本阶段的“资源泄漏”是显式释放/终止义务。`ArrayBuffer` 分配不在范围内。`PixelMap` 因有 `release` 纳入；不由此声称实现了托管堆保留链分析。HomeFlow 中标为 `listener` 的 13 条规则不进入本阶段的能力达标分母。

## 3. 实施方案

### 3.1 目录、接口与旧实现并存

拟议最终结构：

```text
src/analysis/
  resource/                 原 TaintFact、SourceSinkManager、TaintAnalysisProblem、
                            TaintAnalysisSolver、ResourceLeakDetector 等，保持原路径
  resourceleak/
    rules/                  ResourceRule；后续加入规则注册与 HomeFlow 对照规则清单
    ResourceFact.ts         有限资源状态与身份
    ResourceProblem.ts      四种 IFDS 流函数和 Source/Release 语义
    ResourceRunner.ts       复用现有 Scene、DummyMain、DataflowSolver
    ResourceResult.ts       出口收集、原因分类、去重与证据
    index.ts                只导出新资源泄漏接口
```

实施顺序：

1. 原 `resource/` 文件与导入路径保持不变，新建 `resourceleak/`。运行旧资源模块的定向类型检查和测试，确认新增目录没有改变旧诊断。
2. 在 `resourceleak/` 建立独立类型和 Runner，命名为 `ResourceFact`、`ResourceProblem`、`ResourceRunner`，避免旧 `Taint*` 与新类型混用。复用本仓库 [`src/ifds/`](../src/ifds/index.ts) 和 [`src/lifecycle/`](../src/lifecycle/index.ts)，不复制 HomeFlow 求解器或依赖其私有运行时。
3. `ProjectAnalyzer` 增加内部引擎选择（`resourceEngine: 'legacy' | 'new'`）。本阶段默认始终为 `legacy`；真实应用脚本提供显式引擎选择。新结果写入独立的 `newResourceAnalysis` 字段，保留旧 `resourceAnalysis` 现有字段的含义。**默认切换不属于本阶段**：只有旧实现的其他资源规则也迁入并验证，或明确批准缩减产品覆盖后，才另行评审默认值与兼容字段。
4. 规则分批接入：先 7 条句柄规则，再 3 条兼容规则；每批同时补正反夹具与对应的失败原因测试。旧规则不自动导入新引擎，防止混入 `closure`/`memory` 条目或通配 `release` 误消除事实。

新目录接线与新引擎能力验收是两个独立验收点。旧文件没有迁移，因此其深路径导入无需转发或迁移清单。

**第 3.1 节实施记录（2026-09-29）：** 原 `resource/` 的 7 个文件保留原路径且与仓库原版本逐字节一致。`resourceleak/` 中建立了 `ResourceFact`、`ResourceProblem`、`ResourceRunner`、规则与结果类型，未转发任何旧分析接口。`ProjectAnalyzer`、CLI 和真实应用脚本可选择引擎，默认仍为 `legacy`；旧 `resourceAnalysis` 与新 `newResourceAnalysis` 分列。新 Runner 在未配置规则时显式返回 `not-implemented`，使报告和退出状态标记失败；传入精确 API 规则时可运行第 3.2 节的传播与判定。第 4 步的 HomeFlow 具体规则及其逐条夹具尚未实施，不表示新引擎已达到 HomeFlow 能力。

### 3.2 事实传播与判定步骤

1. **创建：** 根据已解析的 `ruleId + allocator API + handleReceiver` 在调用语句生成事实。分配身份使用稳定的调用点和可区分的对象/上下文，不以方法名或资源类型代替实例身份。无可追踪句柄时记录不确定性或规则指定的静态槽位，不随意认定必泄漏。
2. **传播：** 普通边处理赋值、字段、别名与覆盖；调用/返回边映射实参与形参、`this`、返回值和字段；call-to-return 边处理未知调用及摘要。事实域和哈希保持有限；证据路径单独索引，避免把无限历史塞进事实相等性。跨 Ability/Page/Component 的边界沿用当前生命周期建模，遇到未知入口保守处理。
3. **释放：** 同时核对规则配对、资源句柄/别名、事件/定时器标识（适用时）、释放发生的路径。错误对象或错误规则的 `release/close` 不杀死事实。`null` 赋值只在规则明确规定释放义务被解除时生效，不能普遍当作释放。
4. **终点：** 在资源所属生命周期的可达出口上读取 `allocated/released/escaped` 状态。所有权明确交给调用者、容器或外部系统时记录转交证据；所有权未知时标记 `unknown`。部分路径释放、最后句柄被覆盖、错误释放分别保留原因。
5. **报告：** 去重键至少含项目、规则 ID、分配位置、资源身份、原因；报告保留泄漏边界与关键传播/释放证据。抑制必须记录规则和理由，不以同方法出现任何 `close` 就抑制。

**与 HomeFlow 的关系：** [AllocatorDetector](../../homeflow/src/resourceLeak/detector/AllocatorDetector.ts)、[ReleaserDetector](../../homeflow/src/resourceLeak/detector/ReleaserDetector.ts)、[PostProcess](../../homeflow/src/resourceLeak/PostProcess.ts) 提供要达到的语义线索；具体流函数需按 ArkLifeguard 的 IFDS/ICFG API 实现。异步注册并不表示回调立即执行，回调调度与生命周期属于 ICFG/框架边，资源事实映射属于本 Problem。

### 3.2 实施结果（2026-09-29，定向验证）

新引擎接受调用方注入的 `ResourceRule[]`，按完整方法签名和句柄位置匹配创建/释放 API。`ResourceProblem` 实现普通边、调用边、返回边与调用到返回边；同一事实保存有限的别名集合、分配语句、规则 ID、状态和一个关键事件位置。事实相等与哈希不包含不断增长的传播路径，缓存键与哈希以控制重复计算；未使用旧实现的全局 `activeTaints` 删除策略，也未复制 HomeFlow 的求解器。`ResourceRunner` 从可达出口的事实生成报告，区分未释放、部分路径释放、最后句柄覆盖、错误释放和未知所有权。新旧报告字段分离，文本、Markdown、HTML 与 JSON 均可展示新诊断。

| 已验证的能力 | 证据范围 |
| --- | --- |
| 分配点区分、赋值别名、同一资源的精确释放、错误规则释放与错误对象释放 | `test/resourceleak/ResourceLeakFlow.test.ts` 的两分配点、别名和错误释放夹具；错误 API 不会把事实标为已释放。 |
| 条件分支、覆盖、显式允许的空值解除 | 同一文件中的部分释放、覆盖和 `releaseByNullify` 夹具。 |
| 参数传递、返回值、接收者字段跨方法传播 | 同一文件中的直接调用、工厂返回、字段存取正反例。调用者别名在直接调用返回时恢复；有方法体的释放 API 先按精确规则处理。 |
| 生命周期字段释放 | `lifecycle-release` 与 `lifecycle-leak` 两个 ArkTS 夹具：`onCreate` 创建、`onDestroy` 释放时无诊断；去掉释放则报告未释放。 |
| 未知外部调用、容器转交、可选回调与 Promise 回调 | 只产生低置信度 `unknown-ownership`；回调注册不被视为必然执行。此处是保守回退，不证明回调的完整释放语义。 |
| 应用层隔离与报告 | `ProjectAnalyzer` 可注入规则运行新引擎，旧 `resourceAnalysis` 不混入新诊断；报告格式有对应定向测试。 |

**尚未完成的能力与验收：** HomeFlow 的 10 条 `resource` 规则尚未接入默认规则集；SDK 解析状态、静态注册槽位、事件/回调标识配对、重复执行同一分配语句的实例区分、多层字段与容器所有权、精确的 Promise `then/catch/finally` 调度仍需实现或裁决。当前回调/Promise 与未知外部调用会保守降为 `unknown`，因此不能把这部分低置信度结果算作已确认泄漏。证据目前是分配点、关键事件和出口，尚未提供完整跨过程路径。未运行真实应用对照，不能声称达到 HomeFlow 同级能力。旧引擎仍为默认；CLI 未注入新规则时明确失败。

**本次验证：** `npm run typecheck`、`npm run typecheck:test`、`npm run typecheck:scripts` 与 `git diff --check` 均通过；定向运行 `test/resourceleak/ResourceLeakFlow.test.ts`、`test/application/ProjectAnalyzer.test.ts`、`test/report/ReportGenerator.test.ts`、`test/cli/Cli.test.ts`，共 38 项通过。未运行完整测试套件、全量构建或真实应用对照。HomeFlow 相关结论来自本次源码参考，尚无配对实验结果。

## 4. 验收标准

### 4.1 能力门槛：夹具与规则矩阵

- 建立 `HomeFlow 10 条 resource 规则 → 新规则 ID → 创建/释放 API → 句柄位置 → 适用 SDK → 对应夹具` 的机器可读矩阵。10/10 均须有可解析规则；未解析或未实现不能计作覆盖。HomeFlow 原始规则表须固定版本和文件哈希，新增/变化规则需重新评审。
- 每条规则至少一正一反：未释放与正确释放。额外覆盖同名不同对象、错误释放 API、别名、字段、跨方法返回/转交、跨生命周期释放、部分分支释放、覆盖、Promise/回调可选执行。可以借鉴 [HomeFlow MemLeak 夹具](../../homeflow/tests/resources/MemLeak/) 的意图，但需在本仓库按当前 SDK/生命周期模型重建预期。
- 对旧实现的回归另设门槛：新增独立目录后原有资源测试和对照样例的诊断集合不变。新实现的通过条件是**新引擎自身**的夹具 TP/FP/FN 和证据，不借用旧结果充数。
- 单元与集成测试覆盖规则校验、IFDS 流函数、出口判定、应用层结果隔离；每个失败用例可追到具体规则或传播边。公开旧导入路径的兼容性做类型检查。

### 4.2 真实应用对照协议

对照集采用双方脚本都识别的 [`HarmonyRealApps/meta.json`](../HarmonyRealApps/meta.json)。当前列表为 48 个项目，执行前检查每个项目源文件和版本；不得挑选只有零告警的项目宣称通过。对照流程：

1. **固定输入和配置。** 记录两仓库提交、ArkAnalyzer 版本（当前两个仓库的 `package.json` 依赖版本不同）、48 个应用提交或内容哈希、相同物理 SDK 文件树、规则配置哈希、分析入口/生命周期模型、超时、Node 堆上限、硬件与运行命令。HomeFlow 脚本默认 3,600,000 ms/24,576 MB，本仓库脚本默认 180,000 ms/4,096 MB；须修改或覆盖成同一预算后再比较。若入口模型无法一致，列为比较限制，不将时间/告警差异直接归因于新分析。
2. **先小范围核对，再跑全量。** 先选择覆盖非空资源告警与零告警的少量真实应用，确认报告解析、位置映射与双边状态；再对全部共同可分析项目运行。每个项目单独进程、同一超时与内存上限，保留失败/超时记录。此步骤属于耗时真实应用测试，按 `AGENTS.md` 在实际执行前征询用户；本设计阶段不运行。
3. **按诊断逐条配对。** HomeFlow 用 `report.sarif` 的 `ruleId`/位置与 `report.json` 的 `allocLocation`/trace；新报告输出同等信息。规范化键为 `project + 对照 ruleId + 分配文件相对路径 + 行/列 + 泄漏原因/边界`，源映射异常单列。HomeFlow 的 `homeflow.uid/v1` 是其内部指纹，不能直接与新工具指纹字符串比较。只把 10 条 `resource` 规则送入主对照；13 条 `listener`、旧方法内候选与旧引擎结果单独列示。
4. **裁决差异。** 对共同告警、仅 HomeFlow、仅新引擎、位置/原因不一致分别查看应用源码和 API 语义，标记 `确认真阳性 / 确认误报 / 无法判定 / 模型或规则范围差异 / 工具失败`，保存证据与复现命令。HomeFlow 结果不是金标准；未裁决的差异不可自动计为新工具漏报或提升。
5. **出具当前版本报告。** 按项目与规则给出运行状态、共同/单边诊断、人工裁决后的 TP/FP/FN、Precision/Recall（仅在有相应真值时）、分析耗时、IFDS 求解统计与峰值内存。旧快照只能放在历史附录，不能替代本阶段新代码与同一次输入的结果。

可以扩展现有 [ArkLifeguard 真实应用脚本](../scripts/test-resource-real-apps.ts) 的 `--engine` 与诊断字段，HomeFlow 侧已有 [真实应用批处理脚本](../../homeflow/scripts/analyze-harmony-real-apps.ts)，其 `--project`、`--timeout-ms`、`--sdk-root`、`--max-old-space-mb` 与 `--output` 可用于配对执行。HomeFlow 脚本输出 `summary.json`、`diagnostics.json` 和逐项目 `report.sarif`/`report.json`；新脚本需提供稳定的逐项目 JSON，以便规范化比较。两边状态都必须为 `success` 才进入准确率分母；失败/超时不许当作零诊断。

### 4.3 宣布第一阶段完成的条件

1. 新旧资源引擎均可独立运行；旧引擎回归通过，默认仍为旧引擎，新引擎结果有独立报告契约与显式入口。
2. 10 条 HomeFlow `resource` 规则全部实现并通过对应夹具；7 条核心资源规则与 3 条兼容规则在报告中可区分。旧规则迁入状态逐条可见。
3. 全部共同真实应用已按固定配置运行并有完整状态表；共同成功项目的**每条**诊断差异已裁决。不能以两个总数接近、单项目样例通过或旧历史报告宣称达标。
4. 在经人工裁决、非空的真实应用诊断集合上，新引擎对这 10 条规则的 Recall 和 Precision 均不低于 HomeFlow；HomeFlow 已确认的真阳性没有未解释漏报。若真实应用中某规则没有命中，该规则只能由夹具证明语义实现，并在真实应用矩阵中标记“未覆盖”，不得宣称实测达标。
5. 同预算下记录失败/超时与资源消耗；新引擎若对 HomeFlow 成功的项目新增失败或超时，须解决或作为未达标项列出。性能差异必须结合诊断集合、`processedEdges`、`propagationAttempts` 等求解统计解释，不把更快但少传播当作收益。

若真实应用可确认的资源真阳性过少，需补充有源码审查依据的真实应用样本，直到比较具有非空正例与反例；不能降低门槛改用纯夹具结果替代真实应用验收。

## 5. 本文与总体方案的关系

本文只约束第一阶段的资源泄漏检查。闭包/注册和托管内存保留检查仍按[总体拆分方案](./资源闭包内存泄漏检测拆分方案.md)分别设计。第一阶段那三条 HomeFlow 兼容规则在后续迁移时要保持诊断身份和历史映射，避免同一问题被两个检查重复报告。
