# 生命周期约束精化与 LLM 辅助建模实验计划

日期：2026-10-14。状态：研究与实验设计，尚未实施人工补全、LLM 实验或新一轮性能测量。

本文回答两个问题：分层生命周期约束是否值得继续研究，以及如何在已有静态分析框架下设计 LLM 实验。下一步优先开展小规模人工补全实验，先确认准确的生命周期信息能否改善分析，再评价自动恢复这些信息的方法。

## 1. 研究定位与已有证据

研究任务书提出 UI 事件次数、逻辑组件跳转、UI 与逻辑组件交互等多层约束，希望缓解状态膨胀并保持覆盖。任务书还列出了规模、耗时和误报方面的技术指标，见 [研究任务书](基于有界生命周期模型的TypeScript缺陷检测技术研究-终稿.docx)。满足工具指标与证明某种约束带来收益，是两项不同的评价。

目前研究者反馈：分层模型尚未展示更高效率；未知归属 callback 可能重新连接不同 Ability；跨 Ability 传播也可能不占主要成本。精度收益尚待人工标注。上述原因属于待检验假设，不能写成已经证实的瓶颈。

本次源码与文档检查确认：

- 当前 `flat`、`opt-flat` 与 `hierarchical` 均使用循环 CFG。旧的 unroll/K 展开已移除；分层精化实验不依赖展开次数。
- 各 Page scope 可以进入全局 fallback，未知归属 callback 返回后可以进入各 Page scope。因此，剪掉直接跨 Page 边不等于消除传递可达性。
- 当前模型没有完整 Page stack、`router.back`、跨 Ability continuation 和所有动态路由语义。补全 owner 不会自动补齐这些能力。
- CFG 上存在连接，不代表特定 fact 一定沿其传播；传播还取决于流函数。跨 Ability 也不天然非法，合法启动、共享状态与异步交互必须保留。

依据：[生命周期说明](analysis/lifecycle.md)、[分层创建器](../src/lifecycle/HierarchicalLifecycleModelCreator.ts)。

IFDS 会合并相同抽象状态，并不枚举所有具体事件序列。减少事件组合未必减少独立路径边；K 展开还可能增加程序点。因此，不再预设“分层或有界一定加速”，而是检验以下因果链：

```text
补全可靠语义 → 排除不可行事件序列 → 改变独立事实传播 → 改善诊断或成本
```

## 2. 需要回答的研究问题

| 编号 | 问题 | 关键证据 |
| --- | --- | --- |
| RQ1 | 当前约束是否被 fallback 或其他路径绕过？ | 生成图上的传递可达路径，以及实际 fact 传播记录 |
| RQ2 | 人工补全 owner/route 能否改善精度或成本？ | 同一项目、同一配置下的成对对照 |
| RQ3 | owner/route 是否不足，还需要状态与交互约束？ | 精确归属组与增加必要状态约束组的差异 |
| RQ4 | LLM 能否在可验证边界内恢复有价值的信息？ | 对人工真值的恢复质量、下游收益和总成本 |

人工补全组只表示选定样本、约束类型和当前表达能力下的参考结果，不是理论最优上界。若约束没有被正确编译或实际生效，不能据此否定语义精化本身。

## 3. 人工补全实验的范围与分组

### 3.1 首轮规模

建议先选 3～5 个项目、20～30 个建模缺口，并建立至少六类成对微型用例。该规模用于可行性判断，不用于声称普遍有效。实际候选不足时如实记录，不人为制造“真实项目缺口”凑数量。

项目选择应覆盖：单 Ability 多 Page、多 Ability、未知 owner、动态或包装导航、共享组件或多注册来源。同时保留一个 owner 基本可解析的对照项目。记录项目为何入选；这是一组有目的的诊断样本，不能作为总体误报率的无偏估计。

首轮以**空指针检测中的跨回调先后顺序**为主任务：已有受控生命周期用例可以对照“不合法跨 Page 次序造成的误报”与“合法导航后真实空指针缺陷”；现有 scope profiler 能辅助定位主 DummyMain 中的事实传播。先扩充非空差异告警与合法路径反例，再评估真实项目。资源释放可作为第二个分析域复核结论，但其 API 合同和句柄所有权可能成为额外混杂因素。闭包、内存检测还受注册规则、对象身份和寿命边界影响，首轮难以单独归因给生命周期约束。各分析域分别报告，不能把空指针结果直接外推。

### 3.2 四个核心组

| 组别 | 配置 | 允许改变的内容 | 比较目的 |
| --- | --- | --- | --- |
| A | `opt-flat` | 使用现有全局回调组合 | 工程优化一致的基线 |
| B | 当前 `hierarchical` | 使用现有自动 owner/route 恢复 | A→B：现有分层模型收益 |
| C | `hierarchical`＋人工核实 owner/route | 仅补充可核验归属及导航信息 | B→C：信息不完整的影响 |
| D | C＋必要的状态/交互约束 | 对已确认不可行序列增加受限状态规则 | C→D：模型表达能力的影响 |

C 可进一步做“仅 owner”“仅 route”“二者一起”的单因素对照，但只在初步差异值得解释时扩展。D 一次增加一种约束，先逐条记录效果，再评价组合效果。

固定 SDK、项目版本、入口集合、分析规则、调用解析、事实域、调度、预算、超时及 compact dispatcher 设置。首次因果对照建议各组一致关闭可达 Ability 裁剪，避免人工 route 同时改变入口保留集合；如需研究裁剪效果，另设所有组均开启的独立实验。

首轮不引入新的次数约束。若以后重新研究次数敏感性，应作为独立实验，并报告真实缺陷损失、结果保留率与成本；不能仅凭告警数量相同声称覆盖不变。

## 4. 人工补全实验的执行步骤

### 步骤一：冻结输入与登记样本

为每个项目记录项目提交或源码指纹、分析器提交、SDK 版本/路径、入口、分析域、全部配置、硬件和运行环境。确认项目能被解析、入口有实际覆盖；分析失败与零告警必须分开。

建立缺口清单，优先来自当前 fallback、未解析导航和差异告警，另抽取少量没有差异告警的缺口避免只挑“容易改善”的样本。按根因分类：

| 缺口类型 | 例子 | 人工处理方式 |
| --- | --- | --- |
| 可恢复的缺失信息 | 包装函数隐藏了静态页面目标 | 找到完整调用与参数传递证据 |
| 合法多归属 | 同一个组件在多个 Page 创建 | 标注集合，禁止强行选择单一 owner |
| 模型表达不足 | 所属 Page 已知，但回调受注册状态控制 | 留给 D，不能伪装成 owner 补全 |
| 动态信息不足 | 目标来自外部输入 | 标注 unknown，继续保守处理 |
| 前端或调用解析问题 | 回调方法、ViewTree 或目标调用未提取 | 单独记录；如修复，应更新并重跑各组 |

每个缺口的单位尽量是“注册点/创建点＋回调方法＋实例上下文”，而不是仅按 callback 函数名。相同函数可服务多个实例与 Ability；声明所在类不必然等于运行时归属。

### 步骤二：提取现有模型和初始结果

分别保存 A、B 的配置、生命周期报告、告警与统计。检查实际入口、callback 清单、scope 归属和 fallback，确认输入与预期一致。不要仅依赖 `prunedCrossPageTransitions` 等直接候选对统计，要检查 A→fallback→B 等间接路径。

需要输出一张核查表：`callback/registration → 当前 owner 集合 → 是否 fallback → 原因 → 涉及的告警/传播位置`。现有报告若不能提供全部字段，应先补实验导出器；字段缺失不能填成“没有”。

下列命令是当前已有入口的示例，仅供后续执行；本文编写过程没有运行它们。替换绝对路径，先创建输出目录。预计超过两分钟的实验先按项目策略确认范围。

```bash
mkdir -p out/lifecycle-refinement/pilot

npm run inspect:dummymain -- "/absolute/path/to/app" \
  --sdk "/absolute/path/to/ets" --model hierarchical --format both \
  > out/lifecycle-refinement/pilot/hierarchical-ir.txt

npm run cli -- analyze "/absolute/path/to/app" \
  --sdk "/absolute/path/to/ets" --checks resource \
  --lifecycle-model opt-flat --no-prune-unreachable-abilities \
  --format json --output out/lifecycle-refinement/pilot/A-report.json \
  --lifecycle-report out/lifecycle-refinement/pilot/A-lifecycle.json \
  --ifds-stats out/lifecycle-refinement/pilot/A-resource-ifds.json

npm run cli -- analyze "/absolute/path/to/app" \
  --sdk "/absolute/path/to/ets" --checks resource \
  --lifecycle-model hierarchical --no-prune-unreachable-abilities \
  --format json --output out/lifecycle-refinement/pilot/B-report.json \
  --lifecycle-report out/lifecycle-refinement/pilot/B-lifecycle.json \
  --ifds-stats out/lifecycle-refinement/pilot/B-resource-ifds.json
```

IR 检查脚本的配置不一定与 CLI 完全相同，不能把其输出未经核对当作上述正式运行的 CFG。正式实验需从同次运行或配置完全一致的实验入口导出图。

### 步骤三：人工恢复 owner 与 route

对每条缺口按以下顺序检查并记录来源位置：

1. 查看模块配置、入口 Ability、页面清单、`loadContent` 等显式关联。
2. 从 UI 组件创建点、ViewTree 和注册点追踪 callback 实例，确认哪个上下文使它可执行。
3. 检查别名、参数传递、封装方法、共享组件与所有已知调用者，保留多个可能 owner。
4. 对导航追踪目标表达式、包装函数与配置映射。区分“存在目标”与“跳转必然成功”，保留必要的本地继续路径。
5. 查阅固定 SDK 版本的官方文档或实现，核实依赖的平台规则。项目代码事实与平台语义分开记录。
6. 明确能证明什么、不能排除什么；无法建立完整集合时保留 unknown/fallback。

**找到一个 owner 只能证明可能归属。** 若要以集合 `{A}` 替换原来的未知集合，必须说明为何在选定入口和运行假设下可以排除其他 owner。动态加载、未知调用者或未建模注册来源会破坏该结论。

建议使用下列人工标注格式。它是待实现的数据设计，当前没有对应的 JSON 加载接口：

```json
{
  "id": "GAP-001",
  "kind": "callback-owner",
  "projectRevision": "<revision-or-fingerprint>",
  "sdkVersion": "<version>",
  "subject": {
    "callbackSignature": "<full-signature>",
    "registrationSite": "<file:line>",
    "instanceContext": "<creation-site-and-context>"
  },
  "possibleOwners": ["<ability/page-id>"],
  "ownerSetComplete": false,
  "evidence": [
    { "kind": "project-code", "location": "<file:line>", "supports": "<claim>" }
  ],
  "assumptions": [],
  "unresolvedAlternatives": ["<remaining-source-of-uncertainty>"],
  "status": "proposed",
  "reviewer": "<reviewer>",
  "allowedUse": "retain-fallback"
}
```

导航标注另含调用点、可能目标集合、集合是否完整、触发条件、失败/本地继续行为。状态约束另含事件、前置状态、后置状态、对象身份、版本和例外。字段齐全不等于语义成立。

采用 `proposed → reviewed → enabled` 状态流转，有争议标为 `unknown` 或 `rejected`。第二位标注者独立复核所有会删除路径的结论，并记录争议处理；条件不具备时如实说明单人标注局限。标注语义时尽量不展示哪个模型会因此少报，减少迎合预期结果的偏差。

### 步骤四：将人工信息注入实验模型

当前尚无通用人工补全注入接口。下一项最小实现是实验专用的外部标注加载器与绑定日志，不修改被分析应用来“帮助解析”，也不在源码中按项目名硬编码特例。

C 组在收集完成、CFG 构建之前绑定人工信息，输出实际生效的标注 ID、目标方法/注册点、owner/route 前后集合，以及未应用原因。默认配置不启用标注。无法精确绑定或证据不足时继续保守处理。

当前分层实现按组件组织 Page 归属，而人工真值可能细到注册点或实例。如果接口只能表达组件级唯一归属，只有符合这一粒度的标注可直接用于 C；更细信息必须记为 `unsupported`，或先增加所有对照组共用的表达支持，再重建基线。不能把多实例归属强行压成一个 Page。

D 组在模型控制状态中表达必要约束，如受限注册状态、导航前后状态或已核实的生命周期前置条件。保持基础缺陷规则不变；新增状态本身的成本必须计入。不通过把外来 fact 一律删除来模拟不可行路径，也不将长事件历史或 LLM 文本加入 fact 去重键。

每条标注记录：是否加载、是否绑定、是否生效、改变了哪些关系、仍保留哪些 fallback。未生效的标注不能计入“补全后没有收益”。

### 步骤五：先用成对用例验证约束

每种约束至少有一个应排除的非法序列，以及一个必须保留的合法序列。下面是测试类别，不是已经成立的平台语义断言；用例真值需由选定版本的语义和代码建立。

| 类别 | 应验证的精化行为 | 必须保留的反向检查 |
| --- | --- | --- |
| 唯一归属 | 不能在无合法交互条件下任意切入另一 scope | 明确导航到另一 scope 后的真实缺陷仍被检测 |
| 多归属/共享组件 | 按实际实例或上下文处理 | 多个合法 owner 均不被遗漏 |
| 包装导航 | 恢复封装后的目标 | 多目标、失败及本地继续的合法分支仍存在 |
| 页面重入 | 排除有证据的不合法次序 | 合法再次显示、重复事件触发的真实缺陷仍存在 |
| 注册与取消 | 仅在身份及平台保证满足时收紧执行条件 | 不同 listener、排队回调或再次注册不能被错误删除 |
| 合法跨 Ability 数据 | 排除被证明不可能的组合 | 共享状态、消息或启动参数造成的真实联系仍被分析 |

同时检查三层结果：目标事件序列是否仍可达、特定非零 fact 是否传播、诊断是否符合真值。只看“告警消失”不能证明约束正确。

针对 fallback 的关键验证是：补全后旧见证路径是否被阻断；是否还有其他间接路径；必要的合法路径是否保留。只比较直接边数不够。

### 步骤六：人工标注诊断与缺陷真值

按稳定身份对齐告警：项目版本、分析域、规则、缺陷位置，以及必要的分配点/资源/对象身份。统一路径格式、去重规则；不要用展示文本或不稳定内部 ID 对齐。

先标注 A/B/C/D 告警并集，重点检查消失和新增项，再抽查共同告警。每条记录包含：相关代码、事件序列、模型见证、平台规则、合法替代路径、`TP/FP/unknown`、误报根因、复核者。

误报根因分开：生命周期次序、owner/route、别名/对象混淆、条件不敏感、API 规则错误、前端缺失及其他。只有生命周期原因被排除，才能计为该方法的目标收益。

单条展示路径不可行，不代表同一缺陷不存在其他可行见证。反之，真实运行成功复现可支持 TP，未复现不能证明 FP。无法确认的结果保留 unknown，不能为了计算 Precision 强制归类。

告警并集标注不能发现所有漏报。另建独立于分析结果的已知缺陷集合：人工审查或真实修复确认的缺陷，以及明确标识的受控注入缺陷。分别报告真实缺陷和注入缺陷，不合并包装成真实应用召回率。若没有完整真值，只报告已知缺陷检出率，不宣称总体 Recall。

### 步骤七：测量与解释

先运行单次语义对照确认模型与真值，再进行计时。正式计时建议每组一次预热、至少五次独立进程测量，交错或随机化组别顺序，记录中位数与离散程度。开始前确认预计时长；不自动批量执行长实验。

| 层次 | 指标 | 解释边界 |
| --- | --- | --- |
| 信息 | 缺口数、已核实数、unknown、unsupported、生效数、人工分钟数 | 已填字段不等于已解决缺口 |
| 模型 | callback/入口保留、fallback、间接可达性、约束见证 | 模型变小不等于更精确 |
| 求解 | processedEdges、propagationAttempts、finalPathEdgeCount | 指标口径必须来自同一分析域与求解范围 |
| 时间 | 解析、建模、求解、端到端时间 | 求解收益不能替代端到端收益 |
| 质量 | TP、FP、FN、unknown、目标根因 FP、已知缺陷检出 | 告警少不等于精度高 |
| 完成状态 | 超时、失败、预算截断、入口/分配点覆盖 | 失败不能计为零告警或安全 |

对已确认告警计算 `Precision = TP / (TP + FP)`，同时报告 unknown 数和判定覆盖率；有完整标注缺陷集合时才计算对应集合的 `Recall = TP / (TP + FN)`。零分母记为不适用。任务书中的“误报率”应在报告中明确操作定义，不能混淆 `FP/(TP+FP)` 与 `FP/(FP+TN)`。

每项目报告 B→C、C→D 变化，避免仅汇总总耗时掩盖项目差异。结果保留率单列为 `|F_new ∩ F_base| / |F_base|`，它不是召回率。已知 TP 的丢失逐条检查，即使总体告警保留率很高也不能忽略。

## 5. 现有工具能力与待补能力

| 工具/接口 | 可复用内容 | 当前限制 |
| --- | --- | --- |
| [inspect-dummymain](../scripts/inspect-dummymain.ts) | 输出生命周期合成 IR/source | 不提供人工标注注入；输出配置需与正式运行对齐 |
| CLI `--lifecycle-report` | 生命周期结构与收集结果 | 直接候选对统计不能证明传递路径被切断 |
| CLI `--ifds-stats` | 资源 IFDS 求解统计 | 不能当作空指针/闭包/内存的统一统计开关 |
| [scope profiler](../scripts/profile-scope-propagation.ts) | hierarchical 主 DummyMain 空指针求解及 scope 头部事实分布 | 固定模型和部分配置，不覆盖完整工程入口；不能直接完成 A/B/C/D 对照 |
| [SolverStatistics](../src/ifds/SolverStatistics.ts) | 求解工作量和时间字段 | 需确认各 Runner 实际输出及统计边界 |

现有 profiler 以合成实例名近似 fact owner，统计不同 Page 的事实出现在 scope 头部的情况。`foreignFacts` 不是“非法跨 Ability fact”计数，头部事实数量不是传播次数，也不是可节省耗时。多个 Page 求和包含不同程序点，不能称为全程序去重后的事实总数。

若复用 profiler，需要增加同配置模型选择、人工信息绑定和 Page→Ability 映射等实验支持；如增加传播来源追踪，使用旁表并明确开销。细粒度追踪运行与正式计时分开，或保证各组使用一致插桩。

正式比较至少还需要：外部标注加载器、应用日志、间接可达性/见证检查、稳定告警对齐、分阶段计时，以及实验配置清单。未实现这些能力前，不提供虚构的 C/D 命令行选项。

## 6. 继续或停止的判断

| 观察 | 下一步 |
| --- | --- |
| 标注未绑定、未生效，或约束仍被旁路绕过 | 修正实验链路；暂不判断研究价值 |
| C 显著减少目标误报，已知合法缺陷保留 | 继续 owner/route 恢复，优先以精度为贡献 |
| C 无收益，D 有收益 | 转向状态/注册/交互语义；单纯 owner 恢复不足 |
| 路径减少但传播量基本不变 | 说明该路径差异在当前抽象中贡献有限，不继续主张求解加速 |
| 求解更快但端到端无稳定收益 | 定位解析/建模占比，仅报告求解阶段收益 |
| C/D 在有效约束下均无实际收益 | 停止扩大同类约束；检查样本边界，考虑其他建模缺口 |
| 出现已知 TP 丢失 | 暂停启用相关约束，检查归属完整性和平台假设 |

在看结果前约定“值得继续”的成本门槛，例如新增人工成本能否换来多个可复核的目标误报消除、时间改善是否超过测量波动。首轮样本小，门槛用于项目决策，不冒充统计显著性结论。

## 7. 人工实验有效后如何引入 LLM

建议主线：证据约束的生命周期语义恢复与按需精化。静态分析负责定位缺口与最终求解；LLM 检索配置、官方文档和局部源码，提出候选 owner/route/状态规则；检查器或人工核验后才启用。

LLM 输入包含缺口类型、注册/调用点、局部调用与对象关系、相关配置、固定 SDK 证据和允许的约束模板。输出复用人工标注格式，附证据与未排除的情况。禁止凭置信度把可能归属升级为唯一归属，禁止直接删除告警。格式、签名及类型检查只能证明部分结构性质；语义完整性未获证明时保留 unknown。

| 对照 | 作用 |
| --- | --- |
| 当前静态恢复 | 原始基线 |
| 增强确定性规则 | 判断简单解析规则是否足够 |
| 一次性 LLM＋统一检查 | 测基本恢复能力 |
| 缺口驱动检索＋LLM＋统一检查 | 测按需检索与精化的增益 |
| 人工核实信息 | 提供选定约束范围内的参考 |

按项目划分开发集和测试集，先冻结人工真值、提示模板、检查器和预算。记录模型标识、日期、提示、检索证据、工具调用、重试及 token/时间成本；同配置重复运行评价稳定性。检查器预算一致，额外人工复核成本单列。

先测信息恢复正确率、合法 owner/路径被错误排除次数、unknown/拒绝比例，再测下游诊断与成本。完整集合正确性比“猜中一个 owner”更重要。冷启动总成本计入检索、LLM、验证和重分析，缓存复用另报，并绑定项目、SDK、分析器与约束版本防止失效。

可借鉴的工作：

- [Lifestate](https://plv.colorado.edu/bec/papers/verivita-ecoop19.pdf)：描述框架调用与 callback 控制流的协议，启发状态及交互条件建模；其结果不直接证明 HarmonyOS 效果。
- [IRIS](https://arxiv.org/abs/2405.17238)：将 LLM 推断规格与静态分析结合；单纯“LLM 生成规则”不是充分的新颖性主张。
- [LLMDFA](https://arxiv.org/abs/2402.10754)：任务分解并借助外部工具检查部分推理；检查器仍受编码语义与假设限制。

若生命周期人工补全收益很小，可转向[资源语义合同补全方案](agent-assisted-rule-analysis.md)，围绕跨生命周期获取、释放、注册与取消义务改善规则覆盖。该方向的主要贡献是覆盖和检测质量，不能包装成生命周期有界化的效率证明。

## 8. 下一步行动与交付物

按以下顺序推进，每一步验收后再扩大工作量：

1. **确定主分析域与样本。** 登记 3～5 个项目、版本、入口和选择理由，明确首轮只检验哪些约束。
2. **建立缺口与人工真值表。** 盘点 20～30 个候选，先完成少量可核实项；明确 unknown、多归属与表达不足。
3. **实现最小实验接入。** 外部标注加载、精确绑定、生效日志、配置冻结和结果对齐；不改变默认分析行为。
4. **验证成对微型用例。** 证明约束阻断目标非法序列，同时保留合法导航、重入、共享及异步反例。
5. **执行 A/B/C，必要时执行 D。** 先验证语义和差异告警，后做重复计时。长实验事先确认范围。
6. **形成继续/停止报告。** 分别回答模型、传播、精度、时间四层变化，以及未知或未覆盖部分。
7. **仅在有收益的约束上开展 LLM 实验。** 先与增强确定性规则比较，再评价检索和按需精化。

建议实验产物放在 `out/lifecycle-refinement/<run-id>/`，包含 `manifest.json`、`samples.csv`、`gaps.jsonl`、`annotations.jsonl`、`annotation-application.jsonl`、各组原始报告、`diagnostic-labels.csv`、`runs.csv` 和 `decision.md`。这些是计划中的产物名，本文没有创建数据或实验结果。

`decision.md` 必须区分研究者观察、源码检查、人工真值、实测结果与后续假设。本文只完成方案编写与文档静态检查，未修改分析器、未运行测试套件、构建或真实应用实验。
